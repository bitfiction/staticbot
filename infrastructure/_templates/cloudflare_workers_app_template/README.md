# cloudflare_workers_app_template

Per-customer Terraform module that enrolls one app into Staticbot's Workers for Platforms hosting.

**Framework-agnostic.** The TF resources here are pure Cloudflare primitives (Worker script, KV item, Custom Hostname). Framework-specific values (build output path, Worker entry path, asset directory, compatibility flags) live in `template_config` on the `Template` row in staticbot-app's DB and are passed to the wrangler/codebuild steps, not to TF. Same template deploys TanStack Start, Nuxt 3, SolidStart, Astro (CF adapter), or any other framework that produces a Worker bundle.

## Resources provisioned

| Resource | Purpose |
|---|---|
| `cloudflare_workers_script.user_worker` | Placeholder Worker bundle (503). Wrangler overwrites the bundle after TF apply. `lifecycle.ignore_changes` keeps TF from fighting wrangler on subsequent runs. |
| `cloudflare_workers_secret.plain_env` (for_each) | Per-customer plain-text env vars exposed to the Worker. Sensitive secrets are NOT here -- they're pushed via `wrangler secret put` so they stay out of TF state. |
| `cloudflare_workers_kv.route_entry` | Hostname -> user-Worker-name entry in `STATICBOT_ROUTES`. The dispatch Worker reads this on every request. |
| `cloudflare_custom_hostname.customer` | SSL-for-SaaS enrollment so CF issues a cert for the customer's domain. |

## Variable contract

Job vars (rendered by Python tf-worker from `worker_jobs_queue.vars`):

- `account_name` — unique 63-char-max slug, generated by Java
- `cloudflare_account` — `{ account_id, api_token }` (Phase 1: Staticbot's; Phase 2: customer's IntegrationInstance)
- `shared_infra` — refs to `account_bootstrap` outputs (set as tf-worker env vars after account-level apply)
- `app` — `{ worker_name, customer_hostname, plain_env }`
- `worker_secrets` — sensitive map, read by wrangler step only

## Outputs surfaced to downstream jobs

- `worker_name`, `dispatch_namespace_name` -> wrangler_deploy step
- `customer_hostname`, `worker_url` -> smoke_check_http step
- `apex_alias_target`, `dcv_records`, `ownership_verification`, `custom_hostname_id`, `custom_hostname_status` -> CloudflareWorkerAppDeploymentDto for the deployment UI

## State

S3 backend, per-customer state key: `cloudflare-tenants/<account_name>.tfstate`. Same bucket + lock table as other tenants.

## Destroy considerations

- Destroying releases the Custom Hostname (customer's domain stops serving immediately even if their DNS still points at us)
- Destroying removes the KV route entry (dispatch Worker returns 404 for the hostname)
- Does NOT destroy the user Worker uploaded by wrangler -- TF only manages the placeholder; the wrangler-uploaded bundle persists in the dispatch namespace until explicitly cleaned up
- Cleanup of the wrangler-uploaded bundle is a separate step (TBD; track in steps_worker_app.py as `wrangler_undeploy`)
